# 蓝牙调试通道记录（2026-11-12 ~ 11-13）

目标板：AT32F421K8T7 手表，USART2（PA2/PA3，115200 8N1）。
两种模块先后用过：HC-08D（纯 BLE）、HC-04D（双模：经典蓝牙 2.0 + BLE）。

## 通道对比（实测）

| 通道 | 现状 | 一帧 40KB | 备注 |
| --- | --- | --- | --- |
| **HC-04 BLE** | ✅ 可用 | **3.7 s（≈11 KB/s）** | 当前主用 |
| HC-08 BLE | ✅ 可用但极慢 | 4~5 分钟（151 B/s） | 只够做控制 |
| HC-04 经典蓝牙 SPP | ❌ 打不开 | — | 见下节 |
| CH340 有线 115200 | ✅ 可用 | 1~2 s（≈35 KB/s） | 最稳，需接线 |

地址：经典 `04:26:01:08:02:0C`，BLE `C4:26:01:08:02:0C`（首字节差 0x80）。

## 一、SPP（COM8/COM9）打不开

现象：`COM8` 打开 5.2 秒后报「信号灯超时时间已到」，`COM9` 直接卡死不返回。

排查证据（Intel 无线网卡 + Win11）：

| 检查项 | 结果 |
| --- | --- |
| `Bluetooth Device (RFCOMM Protocol TDI)` | Status=OK，**ProblemCode=0**（不是 code 10） |
| 配对记录 | 经典与 BLE 各一条，均在 |
| WinRT `get_rfcomm_services_async()` | 成功，`connection_status` 从 0 变 1，链路能建 |
| 重启蓝牙无线电（`Radio.set_state_async` OFF→ON） | 执行成功，SPP 仍不通 |
| 打开 SPP COM 口 | 仍然 5.2s 超时 / 卡死 |

结论：**不是驱动损坏，是 SPP 通道本身不传数据**。HC-PC 直接建 socket 会抛
`SocketException 0x80004005（提供了一个无效的参数）`，因为它用 InTheHand 绕过系统配对。

绕开：BLE 或 CH340 有线；不要再在「设置」里反复配对，也不要指望 HC-PC 当桥。

## 二、BLE `start notify ... Unreachable`

现象：能连上、能写特征值，但订阅通知失败；WriteClientCharacteristicConfigurationDescriptor
返回成功也没用；模块既不回 AT 也不把数据转到串口（板子 `rx_n` 恒为 0）。

根因：**Windows 缓存的 BLE 配对（GATT 句柄 0035）失效**。

| 尝试 | 结果 |
| --- | --- |
| 板子断电 3 秒再上电 | ❌ 无效 |
| 重启蓝牙无线电 | ❌ 无效 |
| **`DeviceInformation.pairing.unpair_async()`** | ✅ **立刻恢复，ping 108 ms** |
| 管理员删注册表 bond | ✅ 有效，但需要提权 |

工具已内置自愈：连续 3 次连不上 → 自动解绑一次 → 重连；
启动 0.6 秒自动连接，失败每 5 秒重试，最多 15 次。

手动解绑：

```bash
python host/ble_tool.py --addr C4:26:01:08:02:0C unpair
```

## 三、HC-08 的两个坑

1. **不广播**：Windows 一旦配对就会自动连它，连上后 BLE 设备停止广播，扫描不到。
   解决：删 bond 后重启蓝牙；或直接用 WinRT `BluetoothLEDevice.FromBluetoothAddressAsync`
   按地址连（不需要广播）。
2. **带宽**：HC-08 实测只有 151 B/s，40 KB 截图要 4~5 分钟，不适合传图。

## 四、协议要点（详见 README）

- 帧格式 `A5 命令 长度 数据 异或`，合法帧回 `ok`。
- **按键是边沿触发**：必须先发「按下」（`A5 07 01 04`）再发「松开」（`A5 07 01 00`），
  只发按下只生效一次。
- 截图 `A5 06 00` → 回 `A5 11 FF <长度3> <宽2> <高2> <RGB565...> <异或>`。
